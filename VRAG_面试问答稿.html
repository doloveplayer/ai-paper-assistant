一、项目概览

请简单介绍一下 VRAG 项目

VRAG（视觉增强学术研究智能体）是一个面向 CV 学术论文的智能检索与深度研读系统。它解决了传统文本 RAG 在学术论文场景下的三个核心盲区：

  • 图表/公式不可检索 — 纯文本 RAG 丢失了论文中的架构图、消融实验表、数学公式等核心信息
  • 视觉 Token 爆炸 — 全页论文图片每张约 2000 vision tokens，大量无效背景浪费显存
  • 长对话记忆退化 — 传统摘要式压缩导致关键细节丢失，无法跨会话保留用户偏好

我的方案是：ColPali 视觉编码 + BGE-M3 文本编码 双路混合检索 + RRF 融合，配合 LangGraph 状态机编排、四层分层记忆、vLLM Prefix Caching、ColPali ROI 智能裁剪等一系列优化，使整个系统能在单张 RTX 3090 Ti (24GB) 上完整运行。

核心技术指标：支持 16 篇论文/219 页的知识库检索，VLM 视觉分析延迟 5-60s（取决于页面复杂度），ROI 裁剪节省约 60% 视觉 Token，Prefix Cache 命中率 ≥60%。

二、核心技术深度问答

1. 视觉 + 文本双路 RAG 与 RRF 融合

为什么学术论文场景需要双路检索？单路文本 RAG 不够吗？

不够。以 CV 论文为例，一篇目标检测论文的核心贡献往往在架构图（FPN/PANet/Detection Head 结构）、消融实验表、检测结果可视化上。这些信息载体是视觉原生的——纯文本提取要么完全丢失，要么变成不可读的乱码。

举个具体例子：用户问"YOLOv10 的 neck 结构是什么？"

  • 文本路 (BGE-M3)：能命中描述 neck 设计的文字段落
  • 视觉路 (ColPali)：直接命中包含 neck 架构图的页面，即使图上标注文字未被正确 OCR

两路互补：文本路对纯文字描述页召回率高，视觉路对图表/公式页召回率高。我实际测试过纯文本检索（BGE-M3），对 3 个有 ground truth 页面的测试用例，纯文本路的 Recall@3 仅为 0-33%，验证了单路检索的不足。

RRF 融合具体怎么实现？为什么选 RRF 而不是其他融合策略？

RRF（Reciprocal Rank Fusion，倒数排名融合）的核心思想：不依赖分数的绝对大小，只使用排名的倒数。这对异构检索通道（视觉路的 MAX_SIM 分数和文本路的 COSINE 分数完全不可比）至关重要。

来自 tools/vision_rag.py:381-398：

tools/vision_rag.pyL381-398
def rrf_fusion(vision_hits, text_hits, k=60):
    """倒数排名融合算法 (Reciprocal Rank Fusion)"""
    scores = {}
    hit_dict = {}

    for rank, hit in enumerate(vision_hits):
        scores[hit.id] = scores.get(hit.id, 0) + 1.0 / (k + rank + 1)
        hit_dict[hit.id] = hit

    for rank, hit in enumerate(text_hits):
        scores[hit.id] = scores.get(hit.id, 0) + 1.0 / (k + rank + 1)
        hit_dict[hit.id] = hit

    sorted_ids = sorted(scores.keys(), key=lambda x: scores[x], reverse=True)
    return [hit_dict[doc_id] for doc_id in sorted_ids]

为什么 k=60？较大的 k 值使 RRF 对排名变化不敏感——即使某篇文档在视觉路排名第 1 而在文本路排名第 20，它仍有机会在融合后胜出。这是有意为之：我们不希望某一弱的通道过早淘汰好结果。

追问：候选池为什么扩大到 top_k × 6？
RRF 融合前的候选池越大，融合后截断的 recall 越高。我们的策略是：视觉路和文本路各检索 top_k × 6 个候选 → RRF 融合 → 截断至 top_k。这确保了在某一路上排名靠后但在另一路上排名靠前的文档不会被过早丢弃。

2. ColPali Late Interaction 机制

ColPali 和普通的 CLIP/DPR 文本-图像检索有什么本质区别？

本质区别在于向量粒度。CLIP/DPR 将整张图片压缩为单个向量（如 768 维），这导致信息极度压缩——论文页面上的小字标注、图表细节全部被"平均化"丢失。

ColPali 基于 PaliGemma-3B（SigLIP ViT-448px + Gemma-2B 文本解码器），通过 ColBERT 风格的 Late Interaction 保留每个 patch 的独立向量：

  • 每张页面生成 N 个 128 维 patch 向量（N ≈ 32-128，取决于分辨率）
  • 检索时使用 MAX_SIM 比较器：query 的每个 token 与文档的每个 patch 计算 COSINE 相似度，取最大值求和

数学表达：MAX_SIM(q, d) = Σᵢ maxⱼ COSINE(qᵢ, dⱼ)

这意味着 ColPali 支持"图片中的文字检索"——架构图中的标注、实验曲线上的数字、表格中的数据都可以被直接检索到，而不依赖 OCR 预处理。

3. ColPali ROI 视觉 Token 剪枝（核心创新）

全页论文图片送入 VLM 有什么问题？你是如何解决的？

问题：每张高分辨率论文页面图片送入 VLM 时约产生 2000+ vision tokens，其中大量是无效背景（白边、页眉页脚、无关段落）。3 张图就是 6000+ tokens，而 vLLM 视觉服务的 --max-model-len 仅 8192——不优化就直接 OOM。

我的方案——利用 ColPali 自身的 Patch 级相似度热力图进行物理级"去噪过滤"：

完整流程（来自 tools/vision_rag.py:405-584）：

tools/vision_rag.pyL405-480 (热力图 + ROI 裁剪核心逻辑)
def _compute_similarity_heatmap(query_embeddings, image_embeddings):
    """每页计算 32×32 patch 级相似度热力图"""
    # 复用 ColPali query embedding（GPU 端保留）
    similarity_maps = get_similarity_maps_from_embeddings(
        query_embeddings, image_embeddings
    )  # → (32, 32) tensor

def _heatmap_to_roi(heatmap, orig_w, orig_h, top_k=5, context_padding=0.25):
    """热力图 → 像素坐标 ROI"""
    std = np.std(heatmap)
    mean = np.mean(heatmap)
    # 回退机制：无明显热点时退回全图
    if std < 0.3 * mean:
        return []  # 触发全图回退

    # Top-5 峰值 patch → 25% 上下文扩边
    peaks = np.argsort(heatmap.ravel())[-top_k:]
    rois = []
    for peak_idx in peaks:
        py, px = divmod(peak_idx, 32)
        # 网格坐标 → 像素坐标
        cx, cy = px * patch_w + patch_w/2, py * patch_h + patch_h/2
        hw = patch_w * (0.5 + context_padding)
        hh = patch_h * (0.5 + context_padding)
        rois.append({"x": max(0, cx-hw), "y": max(0, cy-hh),
                      "w": min(2*hw, orig_w), "h": min(2*hh, orig_h)})
    return rois  # 去重后返回

关键设计决策：

  • 25% 上下文扩边：纯 ROI 区域可能切断公式符号定义、表格列标题等周边上下文。25% 的 padding 确保保留完整的语义单元
  • 回退机制：热力图标准差 < 0.3×均值 → 说明没有显著热点（query 与全页均匀相关）→ 自动回退全图模式
  • 拼图合成：如果所有页面的 ROI 总数 > 3（VLM 限制 --limit-mm-per-prompt '{"image": 3}'），用 Pillow 将所有 ROI 拼接为一张合成图，规避 API 报错
  • 显存管理：每页计算后 torch.cuda.empty_cache() 释放中间张量
效果：视觉 Token 节省约 60%，同时保留核心图表/公式/表格的完整上下文。

4. 四层分层记忆系统 + 外部化长期记忆

为什么要从传统的摘要式压缩改为分层记忆？各层如何设计？

旧方案的问题：传统做法是把整个对话历史塞进一个 summary 字符串，每次触发压缩时 LLM 再"总结"一遍。两三轮后 summary 越来越模糊——"用户在研究目标检测"这种信息太粗糙，丢失了具体论文 ID、preference 细节。

核心洞察：对话中不同类型的信息有不同的生命周期和更新策略——SOP 永远不变，用户偏好缓慢演变，工具调用中间结果一轮后即可丢弃。

Layer 5（外部化长期记忆）借鉴了 Mem0 的思想——将用户偏好从 Agent 的上下文窗口中"卸载"到外部向量库：

  • 提取：每次回答后在 daemon 线程中调用 LLM 提取记忆事实（格式：「论文关注:xxx」 / 「用户偏好:xxx」），20s 超时静默失败
  • 编码：BGE-M3 将每条事实编码为 1024 维向量
  • 检索：每次用户提问时，用 query 编码 → Qdrant 搜索 Top-3 → 注入 Prompt 动态尾部
  • 非阻塞：提取在独立线程中执行（fire-and-forget），不影响主流程响应

5. vLLM Prefix Caching + 缓存友好 Prompt 排序

Prefix Caching 的原理是什么？你的 Prompt 排序策略为什么能保证 ≥60% 命中率？

vLLM Prefix Caching 原理：当 vLLM 处理一个请求时，它会对 Prompt 的连续前缀做哈希。如果下一个请求的前缀哈希命中缓存，则直接复用已计算的 KV 矩阵，跳过 Prefill 阶段——大幅降低 Time-To-First-Token。

但问题是：如果动态内容（如用户偏好、检索结果）放在 Prompt 头部，每次请求的第一个 Token 就不同 → Prefix Cache 命中率为 0%。

我的解决方案 — 严格静态→动态倒序拼接（agent_core.py:125-156）：

agent_core.pyL125-156 (call_model 中的 Prompt 组装)
# 头部 — 绝对静态（永不变 → vLLM 长久缓存）
system_parts = [core_instructions]

# 中部 — 半静态（滑动窗口，仅尾部变动 → 前半命中缓存）
if working_context:
    ctx_text = "\n".join(
        f"Q: {r['question']}\nA: {r['answer']}" for r in working_context
    )
    system_parts.append(f"## 近期对话上下文\n{ctx_text}")

# 尾部 — 极度动态（紧贴用户 query，每次变化）
if profile:
    profile_text = json.dumps(profile, ensure_ascii=False)
    system_parts.append(f"## 用户画像\n{profile_text}")

# 用户消息 — 本轮新问题
full_system = "\n\n".join(system_parts)

效果分析：假设总 Prompt 长度为 2000 tokens——静态 head 占 800 tokens（100% 命中），半静态 working_context 前 4 轮占 600 tokens（100% 命中），仅尾部 600 tokens 因动态内容变化需要重新计算 → 命中率 ≈ 70%。

关键原则：越不容易变的内容越靠近头部，越动态的内容越靠近尾部。这不是语言层面的优化，而是对 KV Cache 复用机制的工程适配。

为什么选 INT4 而不是 INT8 给 7B 模型？AWQ INT4 将 7B 权重从 14GB → 3.5GB。配合 vLLM PagedAttention，KV Cache 仅占 ~2.5GB。如果用 INT8，权重翻倍到 7GB，ColPali 就没地方了。

为什么 BGE-M3 放 CPU？568M 参数的编码器在 CPU 上单页编码仅需 10-50ms，放 GPU 上反而节约不了多少延迟，但会占 ~4.3GB 显存。这个 trade-off 很明确。

实际瓶颈是显存容量（77% 占用），而非算力（峰值利用率 < 10%）。LLM 推理是典型的 Memory-Bandwidth Bound：每生成 1 个 token 需从显存读取全部 3.5GB 权重，带宽才是限制因素。

  • token_check_router：在 agent 推理前检查 token 数，超过 5000 阈值时先执行 manage_context 裁剪上下文，防止 OOM 和推理速度退化。

  • SQLite Checkpoint：通过 SqliteSaver 持久化，支持跨进程恢复。WAL 模式支持并发读写。

8. 表格空间碰撞检测

PDF 中的表格你是怎么处理的？为什么不用简单的 find_tables()？

PyMuPDF 的 find_tables() 在非标准排版的学术 PDF 上召回率很差（特别是双栏排版、跨页表格）。而且即使检测到表格，如果直接把表格区域的原始文本提取出来——那就是一堆排列混乱的数字，毫无可读性。

我的方案——空间碰撞检测（tools/mix_ingest.py:36-101）：

tools/mix_ingest.pyL36-101 (extract_text_and_tables_from_page)
def extract_text_and_tables_from_page(page):
    # 1. 检测表格 → DataFrame → Markdown
    tables = page.find_tables()
    table_rects = []  # [(table_id, fitz.Rect)]
    tables_payload = {}
    for i, table in enumerate(tables):
        df = table.to_pandas()
        tables_payload[f"TABLE_{i}"] = df.to_markdown()
        table_rects.append((f"TABLE_{i}", fitz.Rect(table.bbox)))

    # 2. 提取文本块（按 Y 坐标排序）
    blocks = page.get_text("blocks")
    blocks.sort(key=lambda b: (b[1], b[0]))  # (y, x)

    # 3. 空间碰撞检测：文本块与表格区域有交集？
    clean_lines = []
    for block in blocks:
        block_rect = fitz.Rect(block[:4])
        overlap = False
        for table_id, t_rect in table_rects:
            if block_rect.intersects(t_rect):
                clean_lines.append(f"[{table_id}_PLACEHOLDER]")
                overlap = True
                break
        if not overlap:
            text = clean_text(block[4])  # 正则清洗
            if text:
                clean_lines.append(text)

    return "\n".join(clean_lines), tables_payload

为什么这样做？

  • 表格区域的原始文本 → 乱码，直接丢弃
  • 插入 [TABLE_0_PLACEHOLDER] 占位符 → 后续 VLM 分析时替换为 Markdown 表格
  • 文本块按 Y 坐标排序 → 保留文档的自然阅读顺序
  • 非表格文本进行正则清洗：滤除 10 位+十六进制乱码、控制字符

9. PDF 安全防线

为什么要做 PDF 安全检查？具体怎么做的？

def scan_pdf_for_malware(file_path: str) -> tuple[bool, str]:
    # 文件大小检查
    if os.path.getsize(file_path) > 50 * 1024 * 1024:
        return False, "文件过大 (>50MB)"

    pdf = pikepdf.open(file_path)
    # 检查全局 JS 注入
    if '/Names' in pdf.root and '/JavaScript' in pdf.root['/Names']:
        return False, "检测到全局 JavaScript 注入"

    # 检查打开动作
    if '/OpenAction' in pdf.root:
        return False, "检测到自动打开动作 (/OpenAction)"

    # 检查页面级触发器
    for page in pdf.pages:
        if '/AA' in page:
            return False, f"页面 {page.label} 检测到自动触发器 (/AA)"

    return True, "安全检查通过"

KV Cache 影响分析：完全无影响。

vLLM PagedAttention 的 KV Cache 生命周期是每个请求独立的：

每个请求的 KV Cache 生命周期: 请求到达 → 分配 KV cache 块 → Prefill(计算 KV) → Decode(复用 KV) → 请求结束 → 释放 KV cache 块 请求 A (带 LoRA): 分配块 [0..7] → Prefill(LoRA 权重) → Decode → 释放 请求 B (无 LoRA): 分配块 [8..15] → Prefill(基座权重) → Decode → 释放 请求 C (带 LoRA): 分配块 [16..23] → Prefill(LoRA 权重) → Decode → 释放
  • KV Cache 不跨请求共享：每次 /chat/completions 调用独立分配 KV cache 块，请求结束后立即释放
  • LoRA 切换在请求边界发生：不同请求可以使用不同 LoRA（或无 LoRA），各自的 KV Cache 完全独立、互不污染
  • Prefix Caching 与 LoRA 兼容：相同 LoRA + 相同前缀的请求之间仍可命中 Prefix Cache；不同 LoRA 的前缀即使文本相同也不共享（因为 KV 值不同）
  • 显存开销极小：LoRA 适配器仅 ~10MB（2.5M 参数 × fp16），远小于基座模型 3.5GB，对显存预算几乎无影响
设计选择：为什么只在摘要时用 LoRA？
摘要是对 RAG 检索文本的"格式化压缩"——输入格式固定（带噪 PDF 文本），输出格式固定（中文 Markdown 摘要）。这是一个边界清晰的子任务，适合用 LoRA 特化。
工具调用（Planner）和通用对话仍使用基座模型，因为它们的推理模式更多样，11 条 Planner 样本远不足以训练出可靠的工具路由能力。
Vision LoRA 为什么没有训练？遇到了什么问题？

根因：AWQ 量化版 Qwen2-VL-2B 的 vision encoder 与训练模式不兼容。

详细诊断过程：

  • 推理模式（model.eval()）正常：含 5040 个 patch 的论文页面图片可以正常通过 vision encoder，输出正确的 logits
  • 训练模式（model.train()）崩溃：vision encoder 内部的 F.scaled_dot_product_attention 抛出 Expected key.size(1) == value.size(1) to be true
  • 梯度检查点是帮凶：开启 gradient checkpointing 后错误复现于 checkpoint 包装的 attention 调用内；关闭后仍失败，但错误信息不同，确认问题在 attention 实现层面
  • SDPA 后端切换无效：依次尝试 flash SDPA（默认）、mem-efficient SDPA、math SDPA、eager attention——均失败，证明不是 attention 后端的问题
  • 正方形/矩形测试图全通过：所有人工生成的测试图（56² 至 840²，以及各种宽高比的矩形）在训练模式下均正常——说明问题与特定论文图片尺寸无关
  • 根本原因：AWQ 量化时的 transformers 版本（≤4.51.3）与当前版本（4.52.4）之间的 modeling_qwen2_vl.py 内部 attention 实现有差异。AWQ 量化过程修改了 attention 权重形状，但训练模式下的反向传播期望原始形状
修复方向：下载非量化版 Qwen2-VL-2B-Instruct（约 4GB），用相同的 29 条视觉数据训练 Vision LoRA，训练完成后再做 AWQ 量化。或者等 AWQ 工具链更新以支持新版 transformers 的 vision encoder。

关键结论

1. Faithfulness Judge 存在文本偏见——双路得分被系统性低估
文本路 Faithfulness=2.6/5，双路仅 2.1/5，但这不代表双路更差。
根因：Faithfulness Judge 只能验证回答是否忠实于文本上下文，无法"看到" VLM 分析的图像内容。
当 VLM 从架构图/表格中提取了文本中没有的事实（如具体的网络层数、实验数值），Judge 会错误地标记为"无依据"。
例如 q002/q007/q009：双路 Faith=0/5，因为 VLM 引用了图表中的细节，而 Judge 在纯文本中找不到对应依据。
这暴露了多模态 RAG 系统评估的核心挑战：如何评估跨模态的忠实度？
2. 检索召回降幅有限（-0.04），但架构/数据集类问题差距显著
总体 Recall 差异仅 0.04，但 q001（模型架构，-0.25）和 q002（数据集，-0.50）差距巨大。
这两类问题的共性：答案高度依赖架构图和实验表——纯文本页面描述不充分。
q005/q006 文本路 Recall 反而更高（+0.25/+0.33），因为目标页面文本描述完整，BGE-M3 语义匹配精准。
3. 排序质量（MRR）完全不受影响（0.80 vs 0.80）
BGE-M3 在"最相关页面排第一"上不输 ColPali。视觉路的增量价值在于召回补充（找回文本路遗漏的图表页），而非排序修正。
4. Answer Relevance 是视觉路最明确的正面贡献（+0.3）
视觉信息帮助更完整地回答问题。q003 的差距最大（文本路 Rel=2/5 vs 双路 5/5），因为该论文的核心方法（因果干预框架）在架构图中表达，纯文本描述不完整。
5. 双路检索的性价比评估
视觉路（ColPali + VLM）额外消耗约 3-4GB GPU 显存和 5-15s 延迟，换来：
▸ Recall +0.04（架构/数据集类问题差距更大）
▸ Relevance +0.3（回答更完整）
▸ Correctness 基本持平
▸ Faithfulness 因 Judge 文本偏见无法公平评估（需多模态 Judge 才能准确衡量）
对于学术研读场景（准确性要求远高于延迟容忍度），双路检索的投入值得，但需要升级 Judge 才能完整评估其价值。

五、文本主路架构升级：从"视觉主路"到"文本主路"的范式翻转

设计动机：整页文本向量的信息稀释问题

旧架构中 BGE-M3 将一整页文本（500-2000 中文字）压缩为单个 1024 维向量。当用户问"用了什么优化器"时，该信息仅占页面的 5%，被其他 95% 内容"平均化"淹没。

纯文本路消融实验证实了这一点：文本路独立 Recall@3 仅 0.525，而双路融合后为 0.57——视觉路（ColPali 多向量）对整页语义起到了补充作用，但也带来了额外的 GPU 负担。

六、系统设计问答

如果要支持 100 个并发用户，你的架构需要怎么改造？

当前瓶颈分析：

  • 单卡 GPU：vLLM 虽然支持 continuous batching，但 7B 模型同时服务 100 个用户的推理请求不现实（单卡稳态约 20-30 tokens/s）
  • ColPali 懒加载：每次工具调用都触发 GPU 模型加载，并发下会显存冲突
  • SQLite 单写：WAL 模式支持 1 写 + N 读，但高并发写会瓶颈
  • 单线程 Agent：同一 thread_id 的 Agent 只能串行执行

ColPali 编码懒加载单实例常驻 GPU 预加载池（2-3 实例）+ 排队锁

检索延迟太长（5-15s）怎么进一步优化？

延迟拆解：文本编码 (50ms) + Qdrant 检索 (10ms) + ColPali 编码 + 热力图计算 (2-5s) + 文本摘要压缩 (2-5s) + VLM 推理 (5-15s)。

优化手段（按收益排序）：

  • ColPali INT4 量化：目前 INT8，降到 INT4 预计节省 1.5GB 显存 + 30% 编码加速
  • VLM 输出长度限制：目前 max_tokens=1024，降至 512 可减半推理时间
  • 异步预编码：在用户阅读上一个回答时就后台编码常见 query 的 ColPali embedding
  • 缓存检索结果：对相同/相似的 query，缓存 RRF 融合后的页面列表（Redis TTL 1h）
  • 流式 VLM 输出：支持 token 级流式展示，用户感知延迟显著降低
如果用更大的模型（如 Qwen2.5-32B）替代 7B，你的系统需要做哪些调整？
  • INT4 量化必须保留：32B 模型 INT4 后约 16GB，单卡 24GB 几乎无法与其他模型共存 → 需要双卡或放弃本地部署
  • vLLM 启用张量并行：双卡环境下 --tensor-parallel-size 2
  • ColPali 独立 GPU：如果 LLM 独占两张卡，ColPali 需要第三张卡或接受 CPU offload
  • 建议：文本推理可以考虑使用 API 服务（DeepSeek/GPT-4），本地仅保留视觉管道
